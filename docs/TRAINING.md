# Обучение моделей на сервере (RTX 4090)

Все модели **опциональны**: без них решатель работает на правилах ЛИ, и приложение полностью
функционально. Модели добавляют три вещи:

| Модель | Что даёт решателю | Данные | Время на 4090 | Где лежит результат |
|---|---|---|---|---|
| **M2** CatBoost-импутация | восстанавливает пропущенные H, D, возраст пород (их нет у 18–29 % строк) — без этого сходство выделов считается по неполным данным | 145 тыс. реальных строк ярусов | 3–6 мин | `models/impute/` |
| **M1** Vydel Encoder (трансформер, self-supervised) | эмбеддинг выдела → признак `emb_cos` «похожи ли выделы как целое» для M3 | 52,6 тыс. выделов | 5–15 мин | `models/encoder/` |
| **M3** LightGBM LambdaRank | выбирает соседа для объединения: учится повторять учителя-перебор (lookahead) и правки специалистов | синтетика + правки из UI | 1–3 мин (+ генерация 5–15 мин на CPU) | `models/ranker/` |
| **M4** LLM-пояснитель (опц.) | переписывает обоснование для пояснительной записки | шаблоны решателя / правки | 30–90 мин QLoRA | `models/llm/` |

Порядок: **подготовка данных → M2 → M1 → синтетика → M3 → (M4)**. M2 и M1 независимы;
M3 использует `emb_cos` от M1, если энкодер уже лежит в `models/encoder` к моменту генерации.

## 0. Окружение

```bash
# Linux-сервер, Python 3.11, драйвер NVIDIA ≥ 550
git clone <repo> hahaton && cd hahaton          # или скопировать папку целиком
python3.11 -m venv .venv && source .venv/bin/activate
pip install -U pip
pip install -r requirements.txt
pip install torch --index-url https://download.pytorch.org/whl/cu124   # под вашу CUDA
pip install -r requirements-ml.txt
python -c "import torch; print(torch.cuda.is_available(), torch.cuda.get_device_name(0))"
```

Положите исходные файлы задачи в корень проекта (как сейчас) **или** в `data/raw/` —
поиск идёт в обоих местах. Нужны три CSV ТО (`Таксационные описания … (выдел|ярус|подрост)_зпт.csv`),
`Лесосеки-1.geojson`, по возможности `Лесосеки-2.geojson` и `Выделы под лесосеками.geojson`.

Проверка, что ядро работает:

```bash
pytest -q                                   # 10 тестов на образце 5_x
python -m forestmerge run --sample --out out/sample
```

Свободной видеопамяти 20 ГБ хватает на всё; модели обучаются по очереди, не одновременно.
Если GPU делят с другими процессами — ограничьте: `CUDA_VISIBLE_DEVICES=0`.

## 1. Подготовка данных (CPU, ~2 мин)

```bash
python -m ml.prepare_data
```

Выход в `data/processed/`:
* `general.parquet`, `layers.parquet`, `undergrowth.parquet` — очищенные таблицы ТО (числа, коды без `.0`,

## 2. M2 — восстановление пропусков (CatBoost на GPU)

```bash
python -m ml.m2_impute.train --device GPU --iterations 5000 --depth 8
```

* Цели: высота, диаметр, возраст породы (`--targets height diameter age`).
* Признаки: порода, ярус, доля в составе, высота/запас/полнота яруса, бонитет, ТЛУ, тип леса, регион,
  год формирования, давность от формирования, **другие известные величины** (при обучении 30 % из них
  случайно скрываются — модель привыкает к пропускам).
* Валидация по **кварталам** (соседние выделы не утекают в тест). Базлайн — медиана по (порода, бонитет, ярус).

Контрольные цифры (CPU, всего 300 итераций — на GPU с 5000 будет лучше):

| цель | MAE модели | MAE базлайна | выигрыш |
|---|---|---|---|
| высота | 2.7 м | 4.4 м | −38 % |
| диаметр | 2.5 см | 6.2 см | −59 % |
| возраст | 8.5 лет | 23.8 лет | −64 % |

Метрики сохраняются в `models/impute/metrics.json` — это готовый слайд для защиты.

Подключение: решатель сам подхватит `models/impute/*` при запуске с моделями
(`python -m forestmerge run --sample --models`, в UI — галка «подключить обученные модели»).
По умолчанию восстановленные значения используются **только для сравнения выделов**; чтобы
подставлять их в выходное ТО, задайте `recalc.use_imputed: true` в `config/norms_2022.yaml`.

## 3. M1 — энкодер выделов (PyTorch, GPU)

```bash
# базовый (~5M параметров), 5–7 мин на 4090
python -m ml.m1_encoder.train --epochs 40 --batch 512
# крупнее (~14M), как в плане
python -m ml.m1_encoder.train --epochs 60 --batch 512 --d-model 384 --layers 8 --lr 2e-4
```

* Вход: выдел = до 12 токенов «порода × ярус» (код породы, ярус, преобладающая ли, доля, возраст, H, D,
  запас породы, полнота и высота яруса) + общий токен (регион, ТЛУ, тип леса, вид земель, хозкатегория,
  класс земель, площадь, запас/га, бонитет, давность формирования, число ярусов).
* Предобучение: masked modeling — 25 % известных чисел, 15 % пород, 20 % общих признаков скрываются,
  модель восстанавливает. bf16 autocast, OneCycle LR, AdamW, сплит по кварталам.
* Лог эпох: `num_mse` (ошибка восстановления чисел в нормированных единицах), `sp_acc` (точность
  восстановления скрытой породы) — их и показывать. Лучший чекпойнт → `models/encoder/encoder.pt`,
  затем экспорт `encoder.onnx` (инференс в приложении — onnxruntime на CPU, < 1 мс на выдел).

Признак успеха: `sp_acc` > 0.6 и `num_mse` заметно падает к 10-й эпохе. Если на валидации переобучение
(val растёт) — уменьшите `--epochs` или `--d-model`.

Отладка без GPU: `python -m ml.m1_encoder.train --epochs 1 --limit 3000 --d-model 64 --layers 2 --out out/smoke`.

## 4. Синтетика для M3 (CPU, параллельно)

```bash
python -m ml.synth.generate --n 4000 --workers 16 --out data/synth
# если есть реальная сеть ФГИС — геометрия будет реальной в 70 % сценариев:
python -m ml.synth.generate --n 4000 --workers 16 --network-file "Выделы под лесосеками.geojson" --seed 2
```

Каждый сценарий:
1. берётся реальный квартал из ТО (6–80 выделов, ≥ 3 насаждения) — реальные сочетания характеристик соседей;
2. геометрия — Вороной с кластерными центрами (или реальная сеть), выделы раскладываются по ячейкам по рангу площади;
3. лесосеки (1–3) ставятся на спелые/высокозапасные выделы: целиком, частично (срез прямой) или реальной
   формой из `Лесосеки-1/2`, плюс шум границы (буфер ±25 м, сдвиг ~8 м, поворот ~1°) — так рождаются
   техосколки и мелкие остатки как в образце;
4. 15 % сценариев — выборочные рубки с объёмами 15–40 % запаса; разряд 1/2/3 и способ таксации случайны;
5. **учитель**: для каждого мелкого фрагмента перебираются все допустимые соседи, квартал доигрывается
   жадно до конца, и сравнивается итоговая цель (нарушения допусков × вес + неоднородность × площадь +
   оставленные мелкие). Метка = ранг кандидата по цели.

Скорость ~2 с на сценарий на ядро → 4000 сценариев на 16 ядрах ≈ 8–10 мин. Каждые `--chunk` сценариев
пишется `data/synth/part-*.parquet`, так что генерацию можно прервать и продолжить с другим `--seed`.

## 5. M3 — ранжировщик соседей (LightGBM LambdaRank)

```bash
python -m ml.ranker.train --synth data/synth --feedback data/app.db --feedback-weight 20
```

* Группа = один фрагмент, строки = кандидаты-соседи, ~70 признаков (`forestmerge/features.py`):
  нормированные различия по признакам обособления п.233–241, нарушения допусков п.215, доля общей
  границы, площади, компактность до/после, тот же исходный выдел, класс земель, `emb_cos` от M1…
* Правки специалистов из веб-приложения (кнопки «Принять», «Присоединить к выбранному») читаются из
  SQLite `data/app.db` и получают повышенный вес (`--feedback-weight`).
* Метрики (`models/ranker/metrics.json`): `top1` — доля фрагментов, где выбор модели совпал с лучшим по
  учителю; `regret` — насколько итоговая цель хуже лучшей; рядом те же метрики для базлайна
  «argmin стоимости правил» (`rules_top1`, `rules_regret`).

Честная оговорка для защиты: на синтетике учитель близок к правилам, поэтому прирост M3 над правилами
небольшой (на 19 смоук-группах правила уже совпадали с учителем в 100 %). Основная ценность M3 —
**дообучение на решениях специалистов**: каждое «не согласен» в интерфейсе становится меткой,
и модель подстраивается под практику конкретного лесничества без правки кода и весов вручную.

Режимы в UI/конфиге (`scoring`): `rules` (по умолчанию), `hybrid` (стоимость правил − вес × балл модели),
`ml` (только модель). Жёсткие запреты ЛИ (совместимость категорий, допуски) работают во всех режимах.

Цикл дообучения на правках:
```bash
# специалисты работают в приложении → накопились правки
python -m ml.ranker.train --synth data/synth --feedback data/app.db
curl -X POST http://localhost:8765/api/models/reload     # подхватить новую модель без перезапуска
```

## 6. M4 — LLM-пояснитель (опционально)

Без дообучения: поднимите любую OpenAI-совместимую модель и задайте переменные — обоснования в карточке
будут дополнены текстом «для пояснительной записки»:

```bash
pip install vllm
vllm serve Qwen/Qwen2.5-7B-Instruct-AWQ --quantization awq --max-model-len 4096 \
     --gpu-memory-utilization 0.6 --served-model-name explainer --port 8001       # ~6–8 ГБ VRAM
export FM_LLM_URL=http://localhost:8001/v1 FM_LLM_MODEL=explainer
```
и в запросе `/run` передать `"llm": true`. LLM **не принимает решений**: она получает готовое решение
решателя (JSON с проверками) и только переформулирует текст; числа и пункты ЛИ берутся из шаблона.

С дообучением (QLoRA, ~14–18 ГБ):
```bash
pip install -r requirements-llm.txt
python -m ml.m4_llm.build_sft --scenarios 1000 --out data/sft/train.jsonl \
       [--rewrite-url http://<большая-модель>/v1]      # перефразировка целей для разнообразия стиля
python -m ml.m4_llm.train_qlora --model Qwen/Qwen2.5-7B-Instruct --data data/sft/train.jsonl \
       --out models/llm/qwen7b-explainer --epochs 2
vllm serve Qwen/Qwen2.5-7B-Instruct --enable-lora --lora-modules explainer=models/llm/qwen7b-explainer \
     --max-model-len 4096 --gpu-memory-utilization 0.85 --port 8001
```
`train_qlora.py` не прогонялся в репозитории (нужен GPU 20+ ГБ). Если `trl`/`peft` другой версии —
сверяйте имена параметров `SFTConfig`.

## 8. Перенос моделей в приложение

Всё, что нужно приложению, — папка `models/`:
```
models/
  impute/   height.cbm diameter.cbm age.cbm meta.json metrics.json
  encoder/  encoder.onnx meta.json (encoder.pt — только для дообучения)
  ranker/   model.txt features.json metrics.json
```
Скопируйте её на машину с приложением (GPU там не нужен) и нажмите «Рассчитать» с галкой
«подключить обученные модели» или вызовите `POST /api/models/reload`.

## 9. Частые проблемы

| Симптом | Причина / решение |
|---|---|
| `CatBoostError: ... GPU` | нет CUDA-сборки CatBoost или драйвера → `--device CPU` (медленнее в 5–10 раз, но работает) |
| `CUDA out of memory` в M1 | `--batch 256` или `--d-model 256` |
| M1 `sp_acc` ≈ 0 | мало эпох/данных (`--limit`), увеличьте `--epochs` |
| генератор: много `ошибок` | битые сочетания геометрии (пропускаются); если > 5 % — пришлите `summary-*.json` |
| ранжировщик: `нет данных` | сначала `python -m ml.synth.generate` |
| модели «не видны» в UI | путь `FM_MODELS_DIR`, затем `POST /api/models/reload`; статус в ответе `/api/config` |
