# Обучение моделей на сервере (RTX 4090)

Все модели **опциональны**: без них решатель работает на правилах ЛИ, и приложение полностью
функционально. Модели добавляют три вещи:

| Модель | Что даёт решателю | Данные | Время на 4090 | Где лежит результат |
|---|---|---|---|---|
| **M2** CatBoost-импутация | восстанавливает пропущенные H, D, возраст пород (их нет у 18–29 % строк) — без этого сходство выделов считается по неполным данным | 145 тыс. реальных строк ярусов | 3–6 мин | `models/impute/` |
| **M1** Vydel Encoder (трансформер, self-supervised) | эмбеддинг выдела → признак `emb_cos` «похожи ли выделы как целое» для M3 | 52,6 тыс. выделов | 5–15 мин | `models/encoder/` |
| **M3** LightGBM LambdaRank | выбирает соседа для объединения: учится повторять учителя-перебор (lookahead) и правки специалистов | синтетика + правки из UI | 1–3 мин (+ генерация 5–15 мин на CPU) | `models/ranker/` |
| **M4** LLM-пояснитель (опц.) | переписывает обоснование для пояснительной записки | шаблоны решателя / правки | 30–90 мин QLoRA | `models/llm/` |

Порядок: **подготовка данных → M2 → M1 → синтетика → M3 → (M4)**. M2 и M1 независимы;
синтетика использует M1 и M2, если они уже лежат в `models/` (те же признаки, что в приложении).

## Быстрый путь: установка и обучение в фоне

```bash
cd /opt/hahaton
chmod +x scripts/*.sh                 # если git не сохранил права на запуск
./scripts/setup_server.sh             # один раз: окружение .venv + зависимости + проверка GPU
./scripts/train.sh run test           # 22 теста: ядро, авторизация, проверка загрузки
./scripts/train.sh start              # ВСЁ обучение в фоне: prepare → m2 → m1 → synth → m3
```

После `start` консоль можно закрыть: процесс отвязан от SSH (`setsid` + `nohup`), лог пишется в
`logs/train_<дата>.log`. Вернувшись:

```bash
./scripts/train.sh status             # идёт ли, на каком шаге, загрузка GPU
./scripts/train.sh log                # смотреть лог вживую (Ctrl+C — выйти из просмотра, обучение идёт дальше)
./scripts/train.sh stop               # остановить
```

Отдельные шаги и параметры:

```bash
./scripts/train.sh start m1 synth m3                       # только эти шаги, по порядку
M1_DMODEL=384 M1_LAYERS=8 M1_EPOCHS=60 ./scripts/train.sh start m1
SYNTH_N=8000 SYNTH_WORKERS=24 ./scripts/train.sh start synth m3
M2_DEVICE=CPU ./scripts/train.sh start m2                  # принудительно на CPU
GPU_WAIT_MIN=120 ./scripts/train.sh start                  # общий GPU занят — ждать до 2 ч, пока освободится память
NETWORK_FILE="Выделы под лесосеками.geojson" ./scripts/train.sh start synth m3
./scripts/train.sh run m2                                  # на переднем плане, без фона
```

Веб-приложение на сервере (тоже в фоне), открыть с ноутбука через SSH-туннель:

```bash
./scripts/app.sh start                # http://127.0.0.1:8765 на сервере
ssh -L 8765:localhost:8765 mblp@<сервер>       # на своём компьютере → http://localhost:8765
./scripts/app.sh stop
```

Альтернатива скриптам — `tmux new -s train`, внутри обычные команды, `Ctrl+B D` — отсоединиться,
`tmux attach -t train` — вернуться.

## 0. Окружение (что делает setup_server.sh)

На сервере команды `python` может не быть — только `python3`. Скрипты сами берут
`.venv/bin/python`, а если окружения нет — `python3`. В ручных командах ниже везде `python3`:
внутри активированного окружения (`source .venv/bin/activate`) это тоже Python окружения.

С окружением (рекомендуется):

```bash
sudo apt install python3-venv          # если python3 -m venv ругается на ensurepip
python3 -m venv .venv
source .venv/bin/activate              # в этой консоли python3/pip — из окружения
python3 -m pip install -U pip
python3 -m pip install -r requirements.txt
python3 -m pip install torch           # на Linux колёса PyPI уже с CUDA 12.x
python3 -m pip install -r requirements-ml.txt
python3 -c "import torch; print(torch.cuda.is_available(), torch.cuda.get_device_name(0))"
```

Без окружения (опционально): `USE_VENV=0 ./scripts/setup_server.sh` — ставит в `~/.local`
(`pip install --user`; на Ubuntu 23.04+ добавляется `--break-system-packages`). Нужен Python ≥ 3.10;
другой интерпретатор: `PYTHON_BIN=python3.11 ./scripts/setup_server.sh`. Своя сборка torch:
`TORCH_INDEX=https://download.pytorch.org/whl/cu124 ./scripts/setup_server.sh`.

Исходные файлы задачи уже лежат в репозитории (корень проекта); можно также класть их в `data/raw/`.
Для бэктеста и реальной геометрии в синтетике нужны ещё `Лесосеки-2.geojson` и
`Выделы под лесосеками.geojson`.

Проверка, что ядро работает:

```bash
python3 -m pytest -q                                   # 22 теста: ядро, авторизация, проверка загрузки
python3 -m forestmerge run --sample --out out/sample
```

Модели обучаются по очереди. Нужно видеопамяти: M2 ≈ 4 ГБ (`M2_GPU_MB`), M1 ≈ 3–6 ГБ (`M1_GPU_MB`).
Перед каждым GPU-шагом скрипт смотрит **фактически свободную** память (`nvidia-smi`): если её мало
(GPU общий и занят другими), шаг идёт на CPU, либо ждёт освобождения до `GPU_WAIT_MIN` минут.
M2 на CPU — 5–15 мин, M1 на CPU — 20–60 мин; результат тот же. Если M2/M1 всё же упали, обучение
продолжается со следующего шага (они необязательные), итог — `status: done_with_errors (...)`.
Если GPU делят с другими процессами — ограничьте: `CUDA_VISIBLE_DEVICES=0`.

## 1. Подготовка данных (CPU, ~2 мин)

```bash
python3 -m ml.prepare_data
```

Выход в `data/processed/`:
* `general.parquet`, `layers.parquet`, `undergrowth.parquet` — очищенные таблицы ТО (числа, коды без `.0`,
  ключ — регистрационный номер выдела);
* `stands.parquet` — плоские признаки выдела (класс земель, преобладающая порода, возраст, H, D, полнота…);
* `summary.json` — сводка, доли пропусков.

Справочник пород `config/species.yaml` уже собран из данных; пересобрать: `python scripts/build_species.py`.

## 2. M2 — восстановление пропусков (CatBoost на GPU)

```bash
python3 -m ml.m2_impute.train --device auto --iterations 5000 --depth 8 --gpu-mem-mb 4096
```

* Цели: высота, диаметр, возраст породы (`--targets height diameter age`).
* Признаки: порода, ярус, доля в составе, высота/запас/полнота яруса, бонитет, ТЛУ, тип леса, регион,
  год формирования, давность от формирования, **другие известные величины** (при обучении 30 % из них
  случайно скрываются — модель привыкает к пропускам).
* Валидация по **кварталам** (соседние выделы не утекают в тест). Базлайн — медиана по (порода, бонитет, ярус).

Результат на сервере (5000 итераций, CPU, ~6 мин на все три цели; валидация по кварталам):

| цель | MAE модели | MAE базлайна | выигрыш |
|---|---|---|---|
| высота | 1.72 м | 4.37 м | −61 % |
| диаметр | 2.33 см | 6.23 см | −63 % |
| возраст | 7.6 лет | 23.8 лет | −68 % |

Метрики сохраняются в `models/impute/metrics.json` — это готовый слайд для защиты.

Подключение: решатель сам подхватит `models/impute/*` при запуске с моделями
(`python3 -m forestmerge run --sample --models`, в UI — галка «подключить обученные модели»).
По умолчанию восстановленные значения используются **только для сравнения выделов**; чтобы
подставлять их в выходное ТО, задайте `recalc.use_imputed: true` в `config/norms_2022.yaml`.

## 3. M1 — энкодер выделов (PyTorch, GPU)

```bash
# базовый (~5M параметров), 5–7 мин на 4090
python3 -m ml.m1_encoder.train --epochs 40 --batch 512
# крупнее (~14M), как в плане
python3 -m ml.m1_encoder.train --epochs 60 --batch 512 --d-model 384 --layers 8 --lr 2e-4
```

* Вход: выдел = до 12 токенов «порода × ярус» (код породы, ярус, преобладающая ли, доля, возраст, H, D,
  запас породы, полнота и высота яруса) + общий токен (регион, ТЛУ, тип леса, вид земель, хозкатегория,
  класс земель, площадь, запас/га, бонитет, давность формирования, число ярусов).
* Предобучение: masked modeling — 25 % известных чисел, 15 % пород, 20 % общих признаков скрываются,
  модель восстанавливает. bf16 autocast, OneCycle LR, AdamW, сплит по кварталам.
* Лог эпох: `num_mse` (ошибка восстановления чисел в нормированных единицах), `sp_acc` (точность
  восстановления скрытой породы) — их и показывать. Лучший чекпойнт → `models/encoder/encoder.pt`,
  затем экспорт `encoder.onnx` (инференс в приложении — onnxruntime на CPU, < 1 мс на выдел).

Признак успеха: `sp_acc` > 0.6 и `num_mse` заметно падает к 10-й эпохе. На сервере (5M параметров,
40 эпох, 86 с на 4090): `sp_acc` 0.77 — скрытую породу восстанавливает по остальному составу и
признакам выдела в 77 % случаев; `num_mse` 0.014 в нормированных единицах. Если на валидации переобучение
(val растёт) — уменьшите `--epochs` или `--d-model`.

Отладка без GPU: `python3 -m ml.m1_encoder.train --epochs 1 --limit 3000 --d-model 64 --layers 2 --out out/smoke`.

## 4. Синтетика для M3 (CPU, параллельно)

```bash
python3 -m ml.synth.generate --n 4000 --workers 16 --out data/synth
# если есть реальная сеть ФГИС — геометрия будет реальной в 70 % сценариев:
python3 -m ml.synth.generate --n 4000 --workers 16 --network-file "Выделы под лесосеками.geojson" --seed 2
```

Каждый сценарий:
1. берётся реальный квартал из ТО (6–80 выделов, ≥ 3 насаждения) — реальные сочетания характеристик соседей;
2. геометрия — Вороной с кластерными центрами (или реальная сеть), выделы раскладываются по ячейкам по рангу площади;
3. лесосеки (1–3) ставятся на спелые/высокозапасные выделы: целиком, частично (срез прямой) или реальной
   формой из `Лесосеки-1/2`, плюс шум границы (буфер ±25 м, сдвиг ~8 м, поворот ~1°) — так рождаются
   техосколки и мелкие остатки как в образце;
4. 15 % сценариев — выборочные рубки с объёмами 15–40 % запаса; разряд 1/2/3 и способ таксации случайны;
5. **учитель**: для каждого мелкого фрагмента перебираются все допустимые соседи, квартал доигрывается
   жадно до конца, и сравнивается итоговая цель (нарушения допусков × вес + неоднородность × площадь +
   оставленные мелкие). Метка = ранг кандидата по цели.

Скорость ~2 с на сценарий на ядро → 4000 сценариев на 16 ядрах ≈ 8–10 мин. Каждые `--chunk` сценариев
пишется `data/synth/part-*.parquet`, так что генерацию можно прервать и продолжить с другим `--seed`.

## 5. M3 — ранжировщик соседей (LightGBM LambdaRank)

```bash
python3 -m ml.ranker.train --synth data/synth --feedback data/app.db --feedback-weight 20
```

* Группа = один фрагмент, строки = кандидаты-соседи, ~70 признаков (`forestmerge/features.py`):
  нормированные различия по признакам обособления п.233–241, нарушения допусков п.215, доля общей
  границы, площади, компактность до/после, тот же исходный выдел, класс земель, `emb_cos` от M1…
* Правки специалистов из веб-приложения (кнопки «Принять», «Присоединить к выбранному») читаются из
  SQLite `data/app.db` и получают повышенный вес (`--feedback-weight`).
* Метрики (`models/ranker/metrics.json`): `top1` — доля фрагментов, где выбор модели совпал с лучшим по
  учителю; `regret` — насколько итоговая цель хуже лучшей; рядом те же метрики для базлайна
  «argmin стоимости правил» (`rules_top1`, `rules_regret`).

Результат на сервере (4000 сценариев → 3713 фрагментов-групп; валидация — 742 группы из отложенных
сценариев; признаки с M1 и M2):

| | top-1 (совпал с лучшим по учителю) | regret |
|---|---|---|
| правила (argmin стоимости) | 82.1 % | 0.114 |
| **M3** | **86.7 %** | **0.089** |

То есть ранжировщик действительно учится «заглядывать вперёд» (учитель доигрывает квартал до конца),
а не просто копирует правила: +4.6 п.п. top-1 и −22 % regret (без признака `emb_cos` от M1 было −11 %). Важнейшие признаки — нарушения допусков,
таксационная дистанция, доля общей границы, число признаков обособления. Вторая ценность M3 —
**дообучение на решениях специалистов**: каждое «не согласен» в интерфейсе становится меткой.
После обучения M1 синтетику и M3 нужно перегенерировать (`./scripts/train.sh start m1 synth m3`) —
тогда в признаках появится `emb_cos`.

Режимы в UI/конфиге (`scoring`): `rules` (по умолчанию), `hybrid` (стоимость правил − вес × балл модели),
`ml` (только модель). Жёсткие запреты ЛИ (совместимость категорий, допуски) работают во всех режимах.

Цикл дообучения на правках:
```bash
# специалисты работают в приложении → накопились правки
python3 -m ml.ranker.train --synth data/synth --feedback data/app.db
curl -X POST http://localhost:8765/api/models/reload     # подхватить новую модель без перезапуска
```

## 6. M4 — LLM-пояснитель (опционально)

Без дообучения: поднимите любую OpenAI-совместимую модель и задайте переменные — обоснования в карточке
будут дополнены текстом «для пояснительной записки»:

```bash
python3 -m pip install vllm
vllm serve Qwen/Qwen2.5-7B-Instruct-AWQ --quantization awq --max-model-len 4096 \
     --gpu-memory-utilization 0.6 --served-model-name explainer --port 8001       # ~6–8 ГБ VRAM
export FM_LLM_URL=http://localhost:8001/v1 FM_LLM_MODEL=explainer
```
и в запросе `/run` передать `"llm": true`. LLM **не принимает решений**: она получает готовое решение
решателя (JSON с проверками) и только переформулирует текст; числа и пункты ЛИ берутся из шаблона.

С дообучением (QLoRA, ~14–18 ГБ):
```bash
python3 -m pip install -r requirements-llm.txt
python3 -m ml.m4_llm.build_sft --scenarios 1000 --out data/sft/train.jsonl \
       [--rewrite-url http://<большая-модель>/v1]      # перефразировка целей для разнообразия стиля
python3 -m ml.m4_llm.train_qlora --model Qwen/Qwen2.5-7B-Instruct --data data/sft/train.jsonl \
       --out models/llm/qwen7b-explainer --epochs 2
vllm serve Qwen/Qwen2.5-7B-Instruct --enable-lora --lora-modules explainer=models/llm/qwen7b-explainer \
     --max-model-len 4096 --gpu-memory-utilization 0.85 --port 8001
```
`train_qlora.py` не прогонялся в репозитории (нужен GPU 20+ ГБ). Если `trl`/`peft` другой версии —
сверяйте имена параметров `SFTConfig`.

## 7. Бэктест на сетях ФГИС ЛК

Когда будут файлы `Выделы под лесосеками.geojson` и `Лесосеки-2.geojson`:

```bash
python3 -m ml.backtest.run --network "Выделы под лесосеками.geojson" \
       --lesoseki "Лесосеки-2.geojson" --lesoseki "Лесосеки-1.geojson" --max-quarters 300
```
Выход `out/backtest/report.json`: базовая линия ФГИС (доля выделов < 0.1/0.5/1 га и многоконтурных
среди затронутых рубкой) и результаты нашего конвейера на кварталах, где сеть «до» восстанавливается
(заменён ровно один выдел). **Скрипт не прогонялся** — файлов нет в репозитории; эвристика реконструкции
взята из PLAN.md 2.1 и требует проверки на данных.

## 8. Перенос моделей в приложение

Всё, что нужно приложению, — папка `models/`:
```
models/
  impute/   height.cbm diameter.cbm age.cbm meta.json metrics.json
  encoder/  encoder.onnx meta.json (encoder.pt — только для дообучения)
  ranker/   model.txt features.json metrics.json
```
Скопируйте её на машину с приложением (GPU там не нужен) и нажмите «Рассчитать» с галкой
«подключить обученные модели» или вызовите `POST /api/models/reload`.

## 9. Частые проблемы

| Симптом | Причина / решение |
|---|---|
| `CUDA error 2: out of memory` (CatBoost) | CatBoost по умолчанию резервирует 95 % **всей** видеопамяти. Исправлено: резерв не больше `--gpu-mem-mb` и свободного − 1 ГБ; при падении `train.sh` повторяет M2 на CPU. Посмотреть, кто занял GPU: `nvidia-smi` |
| `CatBoostError: ... GPU` | нет CUDA-сборки CatBoost или драйвера → `M2_DEVICE=CPU` (медленнее, но работает) |
| `CUDA out of memory` в M1 | `M1_BATCH=256` или `M1_DMODEL=256`; либо `GPU_WAIT_MIN=60` — дождаться свободной памяти |
| `status`: «не запущено», но статус «running …» | старый запуск/зависший процесс: `./scripts/train.sh stop` (добивает и процессы `ml.*`), затем `start` |
| M1 `sp_acc` ≈ 0 | мало эпох/данных (`--limit`), увеличьте `--epochs` |
| генератор: много `ошибок` | битые сочетания геометрии (пропускаются); если > 5 % — пришлите `summary-*.json` |
| ранжировщик: `нет данных` | сначала `python3 -m ml.synth.generate` |
| модели «не видны» в UI | путь `FM_MODELS_DIR`, затем `POST /api/models/reload`; статус в ответе `/api/config` |
